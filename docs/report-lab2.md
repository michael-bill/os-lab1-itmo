## Задание

Для оптимизации работы с блочными устройствами в ОС существует кэш страниц с данными, которыми мы производим операции чтения и записи на диск. Такой кэш позволяет избежать высоких задержек при повторном доступе к данным, так как операция будет выполнена с данными в RAM, а не на диске (вспомним пирамиду памяти).

В данной лабораторной работе необходимо реализовать блочный кэш в пространстве пользователя в виде динамической библиотеки (dll или so). Политику вытеснения страниц и другие элементы задания необходимо получить у преподавателя.

При выполнении работы необходимо реализовать простой API для работы с файлами, предоставляющий пользователю следующие возможности:

1. Открытие файла по заданному пути файла, доступного для чтения. Процедура возвращает некоторый хэндл на файл. Пример:

    `int lab2_open(const char *path).`

2. Закрытие файла по хэндлу. Пример:

    `int lab2_close(int fd).`

3. Чтение данных из файла. Пример:

    `ssize_t lab2_read(int fd, void buf[.count], size_t count).`

4. Запись данных в файл. Пример:

    `ssize_t lab2_write(int fd, const void buf[.count], size_t count).`

5. Перестановка позиции указателя на данные файла. Достаточно поддержать только абсолютные координаты. Пример:

    `​​​​​​​off_t lab2_lseek(int fd, off_t offset, int whence).`

6. Синхронизация данных из кэша с диском. Пример:

    `int lab2_fsync(int fd).`

Операции с диском разработанного блочного кеша должны производиться в обход page cache используемой ОС.

В рамках проверки работоспособности разработанного блочного кэша необходимо адаптировать указанную преподавателем программу-загрузчик из ЛР 1, добавив использование кэша. Запустите программу и убедитесь, что она корректно работает. Сравните производительность до и после.

### Ограничения

- Программа (комплекс программ) должна быть реализован на языке C или C++.
- Если по выданному варианту задана политика вытеснения Optimal, то необходимо предоставить пользователю возможность подсказать page cache, когда будет совершен следующий доступ к данным. Это можно сделать либо добавив параметр в процедуры read и write (например, ssize_t lab2_read(int fd, void buf[.count], size_t count, access_hint_t hint)), либо добавив еще одну функцию в API (например, int lab2_advice(int fd, off_t offset, access_hint_t hint)). access_hint_t в данном случае – это абсолютное время или временной интервал, по которому разработанное API будет определять время последующего доступа к данным.
- Запрещено использовать высокоуровневые абстракции над системными вызовами. Необходимо использовать, в случае Unix, процедуры libc.

### Unit-тестирование

Для проверки работоспособности LRU Cache были написаны unit-тесты:

1. **OpenCloseFile**: Проверяет корректное открытие и закрытие файла через LRU кэш, включая обработку ошибок при повторном закрытии.  
2. **ReadWrittenData**: Убеждается, что данные, записанные через кэш, корректно читаются, проверяя целостность данных после операций записи и чтения.  
3. **WritePersistanceCheck**: Тестирует сохранение данных на диск после закрытия файла, проверяя их через системный вызов.  
4. **SeekOperations**: Проверяет корректность изменения позиции в файле (SEEK_SET, SEEK_CUR, SEEK_END) через кэш.  
5. **DataConsistency**: Тестирует согласованность данных между разными дескрипторами одного файла и гарантирует запись на диск после fsync.
6. **CacheEviction**: Проверяет вытеснение старых блоков из кэша при переполнении, используя стратегию LRU.  
7. **MultipleFilesHandling**: Убеждается, что кэш корректно работает с несколькими файлами, сохраняя их данные изолированно.  
8. **ReopenFile**: Тестирует сохранение данных при повторном открытии файла, проверяя, что кэш не теряет информацию между сессиями.

### Программа-нагрузчик

После того, как мы убедились в корректности работы LRU Cache, мы можем использовать его для тестирования производительности.

Программа-нагрузчик для тестирования LRU Cache находится вот тут: [Программа-нагрузчик](../benchmark/monolith/CacheBenchMacOS.cpp)

Для четкого анализа нагрузчика были реализованы следующие сценарии:

1. **RandomRead_Cached**: Измеряет скорость случайного чтения через LRU кэш, эмулируя доступ к случайным блокам большого файла при отключенном системном кэше.  
2. **RandomRead_Uncached**: Служит базовым замером скорости случайного чтения без кэша через `pread`, для сравнения с кэшированной версией.
3. **MixedWorkload_Cached**: Тестирует производительность кэша при смешанной нагрузке (70% чтения, 30% записи), проверяя влияние операций записи на кэш.
4. **MixedWorkload_Uncached**: Аналогичная смешанная нагрузка без кэша с явной синхронизацией (`fsync`), для сравнения накладных расходов.
5. **TightAreaRandomRead_Cached**: Оценивает эффективность LRU при частом доступе к небольшой «горячей» области, где кэш должен минимизировать обращения к диску.  
6. **TightAreaRandomRead_Uncached**: Базовый замер доступа к «горячей» области без кэша, демонстрирующий преимущества кэширования в таких сценариях.
7. **WarmedCache**: Измеряет скорость чтения после предварительного прогрева кэша (весь файл в кэше), показывая идеальную производительность для закэшированных данных.  
8. **ColdCache**: Тестирует «холодный» старт — чтение без предварительного кэширования, имитируя худший сценарий для сравнения с прогревом.
9. **SequentialRead_Cached**: Проверяет скорость последовательного чтения через кэш, оценивая эффективность при линейном доступе.  
10. **SequentialRead_Uncached**: Замер последовательного чтения без кэша, выявляющий выгоду кэширования в линейных операциях.  

Каждый бенчмарк имеет пару (_Cached/_Uncached) для сравнения производительности реализации LRU кэша с «сырыми» системными вызовами, что позволяет оценить эффективность кэширования в разных сценариях.

Результат при следующих параметрах:

- Размер блока для чтения: 4096 байт
- Размер кэша: 2048 блоков
- Размер файла: 64 mb

1. **RandomRead_Cached**: Кэширование *замедлило* случайное чтение (33.7 ms vs 15.5 ms) — вероятно, из-за частых промахов кэша (8 MB кэш vs 64 MB файл) и накладных расходов на LRU-алгоритм.  
2. **MixedWorkload_Cached**: Кэш ускорил смешанную нагрузку в 22.6 раза (50.1 ms vs 1134 ms), так как буферизация записей и чтение из памяти снизили количество обращений к диску.
3. **TightAreaRandomRead_Cached**: Для локальных данных кэш дал ускорение в 4.2 раза (2.32 ms vs 9.70 ms) — LRU эффективно удерживает «горячие» блоки.
4. **WarmedCache**: Чтение из кэша после прогрева занимает микросекунды (3.75 µs), что в ~300 раз быстрее «холодного» доступа (1142 µs).
5. **SequentialRead_Cached**: Последовательное чтение с кэшом *медленнее* (14.4 ms vs 9.97 ms) — что в целом логично, ведь в последовательном чтении нет повторного доступа к блокам и время падает из-за накладных расходов работы LRU-алгоритма.

**Общий вывод**:
- **Кэш выгоден для**:
  - **Локализованного доступа** (TightArea: +4.2x)
  - **Смешанных нагрузок** (Mixed: +22.6x)
  - **Повторного использования данных** (Warmed: +300x)  
- **Неэффективен** для:
  - **Случайного чтения** больших данных (промахи кэша)
  - **Последовательного доступа**
